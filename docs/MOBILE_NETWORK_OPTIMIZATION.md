# 移动端网络优化方法论与 AsterNet 改造路线

> 资料范围：52im《移动端弱网优化专题（一）》至《（十五）》；技术结论同时按现行 IETF RFC 和平台能力校正。本文面向 AsterNet 的 HTTP/1.1、HTTP/2、HTTP/3 客户端，而非某一特定业务 App。
>
> 核心原则：网络优化不是调大超时、增加重试或强制 QUIC，而是建立“可观测 -> 可判定 -> 可控执行 -> 可验证回滚”的闭环。正常网络的尾延迟、切网和 DNS 偶发故障，同样应纳入优化范围。

## 1. 目标与边界

### 1.1 目标

优化以用户任务为目标，分层衡量：

| 层级 | 主要目标 | 核心指标 |
| --- | --- | --- |
| 可用性 | 请求和任务完成，不产生重复副作用 | 任务成功率、请求成功率、降级成功率、白屏率 |
| 时延 | 缩短连接和首字节的长尾 | DNS/Connect/TLS/TTFB/Total 的 P50/P90/P95/P99 |
| 稳定性 | 切网、UDP 受限、抖动和丢包下可恢复 | 恢复时长、迁移成功率、崩溃率、协议黑名单命中率 |
| 成本 | 不用无效请求换指标 | 重试放大率、预连接命中率、流量、耗电、服务端 QPS |
| 安全 | 优化不削弱身份和传输保护 | 证书错误率、SNI/Host 校验率、异常配置命中率 |

### 1.2 不可突破的边界

- 不关闭 TLS 证书链、主机名或 SNI 校验；IP 直连也必须使用原始域名完成 SNI 和证书校验。
- 不对非幂等请求自动重试、自动跨协议重发，除非业务提供幂等键并在服务端去重。
- 不以系统“已联网”、信号格数或单次 RTT 作为网络可用或弱网的唯一判定。
- 不通过无限预连接、并发竞速、心跳、探测或重试掩盖问题；每类操作必须有预算、限流和远端开关。
- 不把过时的内核参数作为客户端通用优化手段，例如 `tcp_tw_recycle`、固定 MSS、固定 Socket 缓冲区或固定初始 RTO。

## 2. 总体闭环

```mermaid
flowchart LR
    A[端侧请求与网络上下文] --> B[分阶段指标和错误归因]
    B --> C[网络质量状态机]
    C --> D[DNS/地址/协议/重试/降级决策]
    D --> E[统一网络执行层]
    E --> F[服务端与端侧聚合分析]
    F --> G[灰度实验与配置回滚]
    G --> C
```

1. **测量**：对每次请求记录 DNS、建连、TLS/QUIC 握手、TTFB、下载、取消、协议、目标地址和最终结果。
2. **判定**：融合请求历史、网络切换、双栈可达性与目标 Host 健康度，区分端侧链路问题、DNS 问题、UDP 不可用、服务端问题和业务错误。
3. **执行**：按请求幂等性、优先级、剩余 deadline 与当前质量选择地址、连接、协议、重试和业务降级。
4. **验证**：分网络、地区、运营商、IPv4/IPv6、协议和业务优先级做实验；没有护栏指标与一键回滚的策略不发布。

## 3. 可观测性：所有优化的前置条件

### 3.1 每请求最小事件模型

使用单调时钟，统一 `request_id` 和 `trace_id`。指标值可为空，但不能伪造为 0。

| 阶段 | 必采字段 | 用途 |
| --- | --- | --- |
| 请求 | host、端口、方法、幂等性、优先级、配置版本、总 deadline | 判断策略是否正确 |
| DNS | resolver 类型、缓存命中、TTL、候选地址、选中地址、解析耗时/错误 | 定位污染、过期、地址选优问题 |
| 建连 | IP 家族、开始/结束、TCP 或 QUIC、复用/新建、失败原因 | 分析双栈、网络和连接池效果 |
| 安全握手 | ALPN、TLS 版本、会话恢复、0-RTT 尝试/接受、证书错误 | 衡量握手优化且保证安全 |
| HTTP | TTFB、响应码、下载字节与耗时、取消原因 | 分离服务端慢与网络慢 |
| 策略 | 原计划、实际协议、fallback 原因、重试次数、断路器状态 | 评估策略代价 |
| 网络上下文 | 网络句柄、Wi-Fi/蜂窝、网络切换序号、IPv4/IPv6 可用性、运营商/地域的脱敏标签 | 支持分层分析 |

不得记录 URL 查询参数、响应正文、SSID、完整 IP 与可识别用户数据；采用采样、哈希或聚合桶，且遵守隐私规范。

### 3.2 主动与被动诊断

- **被动优先**：从真实请求取 `transport_rtt`、TTFB、吞吐、失败率、连接复用率和协议降级率；这是最接近用户体验的信号。
- **主动按需**：只在连续失败、白屏、切网或低频抽样时进行 DNS、HTTPS connect、IPv4/IPv6 可达性探测。探测要分阶段立即落盘/上报，避免进程退出后丢失证据。
- **对照目标**：同时探测业务 Host、稳定探针 Host 和 HTTPDNS Host，防止将服务端故障误判为断网。
- **白屏取证**：保存最近 N 次关键请求和资源加载的环形缓冲；白屏后的探测仅辅助判断，根因以触发前的时序证据为准。

### 3.3 聚合与告警

按 `app_version × 配置版本 × host × 协议 × 网络类型 × IPv4/IPv6 × 地域/运营商` 聚合。重点观察成功率、P95/P99、fallback、重试放大、DNS 命中、连接复用和 0-RTT 命中。以同分层基线判断回归，禁止使用全量平均值掩盖长尾问题。

## 4. 网络质量判定

### 4.1 状态机而非单阈值

建议状态：`OFFLINE`、`CAPTIVE_OR_UNVERIFIED`、`DEGRADED`、`HEALTHY`、`UNKNOWN`，并单独标记 `DNS_FAILURE`、`IPV6_PATH_FAILURE`、`UDP_BLOCKED`、`ORIGIN_FAILURE`。状态只用于调整策略，不应替代单个请求的真实结果。

判定信号的优先级：

1. 连续真实请求的成功率、TTFB 与 `transport_rtt` 趋势。
2. 网络切换通知、网络句柄变化和系统验证状态。
3. 在异常时执行的 DNS/HTTPS/双栈探测结果。
4. 吞吐：仅在传输字节、时长和并发可解释时使用。
5. 信号强度：仅作辅因，不作为决策依据。

使用时间衰减的中位数或分位数，并设置进入/退出不同阈值、最小样本量和冷却时间，避免网络状态在边界来回抖动。阈值必须按业务、地域和目标服务用线上数据标定，不能直接照搬 2G/3G/4G 标签或文章中的固定毫秒值。

### 4.2 按网络质量分层的动作

| 状态 | 网络库动作 | 业务建议 |
| --- | --- | --- |
| `HEALTHY` | 正常连接复用；仅对高置信关键路径预连接 | 正常加载和低优先级预取 |
| `DEGRADED` | 收紧并发和投机行为；优先复用；使用剩余 deadline；幂等请求有限退避 | 优先关键资源，暂停预加载，图片/媒体降质 |
| `DNS_FAILURE` | 启用受控 DNS 回退链；保留安全校验 | 提示可重试，不伪装成业务空数据 |
| `UDP_BLOCKED` | 对该网络上下文暂时跳过 H3，优先 H2/H1 | 不影响用户任务 |
| `OFFLINE` | 快速失败或排队到网络恢复；不做密集重试 | 展示离线内容/本地缓存，待网络恢复再同步 |

## 5. DNS 与地址选择

### 5.1 解决的问题

Local DNS 可能出现超时、劫持、污染、错误地域调度、IPv6 不可达或频繁变更。DNS 优化的目标是减少解析链路时延、提高地址正确性和可用性，而不是永久绕过 DNS。

### 5.2 推荐的解析链与缓存

```text
内存缓存（未过期）
  -> 受认证的 HTTPDNS/DoH 结果
  -> Local DNS
  -> 已签名的短期应急地址
  -> 失败并记录原因
```

- 缓存键至少包含 `host + 网络上下文 + 地址族`；遵守 TTL，并支持短时间 `stale-while-revalidate`，过期上限由服务端配置。
- HTTPDNS/DoH 返回必须经 TLS 保护，并有响应签名或等效可信身份保障；配置包含版本、签名、TTL、撤销和灰度范围。
- 启动和网络切换时可批量预取核心域名；失败时不覆盖最后一次有效结果。
- 按地址记录近期建连成功率和耗时，在服务端排序的候选集上做端侧小幅动态排序，避免所有客户端同步打向同一地址。
- 支持 IPv6-only、双栈和 NAT64。采用 RFC 8305 Happy Eyeballs：IPv6 优先、IPv4 错峰竞速、首个成功即取消其余尝试；延迟和并发上限配置化。

### 5.3 IP 直连的安全要求

IP 直连只适用于受控地址来源和有明确收益的核心域名。仍必须保留原始 `Host`、SNI 和证书主机名校验；不得以自定义 `HostnameVerifier`、跳过证书校验或降级 HTTP 来“修复”直连。动态地址的分发、缓存、撤销与回退均需远端可控。

## 6. 连接、会话与切网

### 6.1 优先级

减少 RTT 的最有效通用方式，是减少不必要的新建连接。为每个 `origin + proxy + TLS 配置 + 网络上下文` 管理连接，支持：

- HTTP/1.1 Keep-Alive、HTTP/2 多路复用和 HTTP/3 多 stream 复用。
- 空闲/最大生命周期/错误逐出、并发 stream 上限、连接级拥塞保护和单飞建连。
- 受预算限制的预连接：只服务于高概率、关键且近期将发起的请求；统计命中率、空耗率、流量和耗电。
- TLS 1.3 会话恢复；0-RTT 仅用于明确安全可重放的幂等请求，并处理服务端拒绝和重放风险。
- 每 origin 的连接池隔离，防止一个 Host 或大响应耗尽所有可用连接。

HTTP/2 消除了 HTTP 层队头阻塞，但单个 TCP 包丢失仍会阻塞同连接所有 stream。HTTP/3/QUIC 可减少这种传输层队头阻塞，并支持连接迁移；其价值须通过分网络实验验证，UDP 受限时必须快速回退 H2/H1。

### 6.2 网络切换

Android 应监听 `ConnectivityManager.NetworkCallback`，将网络句柄、可用地址族与切换序号传给 C++ 核心：

1. 旧网络失效时标记该网络上的 TCP/H2/H1 连接不可复用，取消投机任务。
2. H3 连接优先进行路径验证/迁移；失败后只对幂等在途请求执行一次受预算约束的重连或降级。
3. 新网络触发核心域名 DNS 刷新与有限预连接，不继承旧网络的地址质量结论。
4. 用户取消、后台限制、服务端限流或 deadline 耗尽时，立即停止迁移、重试和预连接。

### 6.3 超时与 deadline

为每个请求设置端到端单调 deadline，并将剩余预算传递给 DNS、地址竞速、连接、TLS/QUIC、TTFB 和下载。超时应按请求优先级、用户是否前台等待、网络质量和历史分位数动态配置。区分连接超时、读写空闲超时、首字节超时和整体 deadline，避免一个宽泛的固定超时掩盖阶段问题。

## 7. 协议、传输与请求调度

### 7.1 协议选择

- 默认以可用性为先：`H3 -> H2 -> H1` 的 fallback 只适用于幂等请求或具备幂等键的操作。
- 将 H3 失败按网络上下文和 origin 记录短期断路器；区分 UDP 不可达、握手失败、证书失败和应用错误，避免误伤正常网络。
- 使用 `Alt-Svc` 或受控配置发现 H3，不对未知 Host 盲目探测。
- 每次 fallback 消耗同一个总 deadline。保留真实协议和失败原因，便于判断 H3 是否确有增益。

### 7.2 数据与请求形态

- 避免小而频繁的请求；合并可安全合并的请求，批量返回，减少 RTT 和头部开销。
- 通过缓存、条件请求、预测加载和断点续传减少重复传输；弱网下降低预加载优先级。
- 对文本内容评估 gzip/Brotli/Zstd 与 CPU、耗电、数据类型的权衡。已压缩的图片、音视频通常不应再次压缩。
- 使用适合业务的紧凑编码（例如 Protobuf）可减少负载，但协议演进、可观测性和兼容性优先于单纯压缩率。
- 将关键小请求、普通 API、大下载/媒体分级队列；大流量不能阻塞用户操作。HTTP/2/H3 的 stream 优先级要与实际服务端调度共同验证。

### 7.3 重试、熔断与降级

重试是最后的可靠性工具，不是默认的性能工具。

- 只重试可重试错误和幂等请求；HTTP 语义错误、证书错误、用户取消及明确的业务拒绝不重试。
- 采用有限次数、指数退避与随机抖动；限制单请求、单 origin、单网络的总预算和并发重试数。
- 断路器按 `origin + 协议 + 网络上下文` 记录连续可重试失败，成功后逐步恢复；冷却和半开探测配置化。
- 服务端返回过载或限流时尊重 `Retry-After`，并让低优先级请求先降级。
- 业务降级包括文本优先、低清媒体、分页缩小、使用缓存和延迟同步；安全校验、下单/支付等一致性约束不能降级。

## 8. CDN、跨境与资源加载

- 采用就近接入、运营商覆盖和多 CDN 容灾；端侧按网络/地域/目标 IP 采样，云端拨测与真实端侧数据互证。
- 通过受控 DNS 或服务端调度选择候选节点，端侧依据近期成功率、TTFB 和连接耗时做有限排序；不能仅依据地理距离。
- 跨境链路要分别统计出境网络、DNS、CDN、TLS/QUIC、源站和资源类型；为不同地区配置独立节点、回源和协议策略。
- 资源白屏场景同时观察 HTML/API、图片、字体、脚本和 CDN 域名，保留关键资源的失败时序和缓存状态；不要只对“白屏后”做单 Host ping。
- 大文件使用分块、校验、断点续传与合理并发；弱网或高流量时降低并发。并发数由端侧网络质量、服务端能力和数据验证决定。

## 9. AsterNet 当前基线

| 能力 | 当前状态 | 依据 |
| --- | --- | --- |
| 协议降级 | 已实现 H3 -> H2 -> H1；仅幂等且可重试错误会继续 fallback，并共享总超时预算 | `sdk/cxx/engine/protocol_selector.cpp` |
| 断路器 | 已有 host × 协议的内存断路器，默认连续 3 次失败冷却 60 秒 | `sdk/cxx/engine/protocol_selector.{h,cpp}` |
| TLS 安全 | 默认校验证书链与主机名，可加载 CA；仅测试开关允许不安全 TLS | `sdk/cxx/platform/tls.cpp` |
| 连接复用 | 未实现；H1 强制 `Connection: close`，H2/H3 均为单请求新建后释放 | `sdk/cxx/engine/http1_engine.cpp`、`quic_engine.cpp` |
| 切网 | ABI 存在 `on_network_change`，核心实现仍为空 | `sdk/cxx/abi/abi.cpp`、`sdk/cxx/client.cpp` |
| 地址策略 | DNS 后顺序尝试地址；无缓存、HTTPDNS、地址质量或 Happy Eyeballs | 各 engine 的解析/连接逻辑 |
| 网络质量 | 接口/设计存在，但尚未采集、判定或上报 | `sdk/cxx/sdt/quality_prober.h` |
| 指标 | API 暴露 DNS/Connect/TLS/TTFB/Total，但当前多项阶段耗时未赋值；诊断为空 | `sdk/cxx/engine/engine.h`、`sdk/cxx/client.cpp` |
| H3 高级能力 | XQUIC 支持基础请求；0-RTT session/TP 持久化、迁移和连接池未实现 | `sdk/android/README.md` |

因此，近期不应先做 TCP 参数调优或盲目扩展 H3 灰度。首先补齐复用、切网、阶段指标和实验基础，才能量化任何协议优化的收益。

## 10. AsterNet 改造路线

### P0：建立真实性指标和验证基线

1. 填充所有引擎的 DNS、Connect、TLS/QUIC handshake、TTFB、Total 及错误阶段；响应中明确 `connection_reused`、`fallback_reason` 和 `attempt_count`。
2. 实现可采样、可脱敏的指标 sink 与请求级 trace，不把日志回调当作指标系统。
3. 修正文档与 API 表述：尚未实现的连接池、迁移、0-RTT、完整阶段指标与诊断不能标记为已具备。
4. 新增确定性测试：总 deadline 递减、幂等 fallback、断路器、取消和并发销毁竞态。

**验收**：100% 请求均可归因至成功、取消或明确失败阶段；不会把未测量阶段显示为 0；现有 AUTO 行为无回归。

### P1：连接管理和安全会话恢复

1. 建立按 origin 隔离的连接管理层，优先实现 H2/H3 复用、连接健康检查、空闲逐出、stream 并发上限和单飞建连。
2. 将 H1 改为可复用 Keep-Alive，但设置空闲/最大寿命/服务端关闭处理；复用失败必须能安全重建。
3. 加入 TLS 1.3 session ticket 缓存；为 H3 安全持久化 session/transport parameters。0-RTT 只接受显式幂等请求。
4. 基于复用率和需求预测引入小预算预连接，并默认关闭，通过灰度证明收益后开启。

**验收**：正常网络下连接新建数显著下降，P95 不劣化；复用、空闲逐出、服务端 GOAWAY/关闭和并发请求均有测试；0-RTT 不会用于非幂等请求。

### P2：网络感知、双栈和切网恢复

1. Android 接入 `ConnectivityManager.NetworkCallback`，向 C ABI 传递网络切换和网络上下文；不要只依赖 `NetworkInfo`。
2. 在新网络上刷新核心域名、清理旧连接；实现 H3 路径验证/迁移，失败后按幂等性重连或协议降级。
3. 加入 DNS 内存缓存、地址健康度、IPv4/IPv6 Happy Eyeballs 和可回滚的 HTTPDNS/Local DNS/应急地址链。
4. 实现网络质量状态机，将其用于收紧预连接、地址竞速、超时和请求优先级，而非强制某个协议。

**验收**：Wi-Fi 与蜂窝切换、IPv6-only、DNS 超时/错误地址、UDP 阻断均可复现；关键幂等任务的恢复时间和成功率优于基线，重试放大受护栏约束。

### P3：策略平台与业务协同

1. 远端配置化 DNS、地址、H3 可用性、超时、断路器、预连接和弱网降级策略；配置必须签名、版本化、灰度并可一键回滚。
2. 接入端侧/服务端指标闭环，按网络分层做 A/B；为 CDN 与跨境链路加入目标 IP 和节点级健康度。
3. 提供请求优先级、幂等键、缓存和资源类型接口，让业务明确参与重试与降级决策。

**验收**：每项策略都有目标指标、护栏、实验样本量和回滚条件；未证明收益的策略保持关闭。

## 11. 测试与发布门禁

### 11.1 故障注入矩阵

| 场景 | 注入项 | 验证重点 |
| --- | --- | --- |
| 正常网络 | Wi-Fi/蜂窝、IPv4/双栈/IPv6-only | 复用率、P95/P99、无性能回归 |
| 弱网 | 延迟、抖动、2%/5% 丢包、限带宽、乱序 | deadline、成功率、尾延迟、重试预算 |
| DNS | 超时、污染/错误地址、HTTPDNS 不可用、TTL 过期 | 回退链、安全校验、地址选择 |
| 传输 | UDP/443 阻断、TCP connect 失败、TLS 失败、服务端 GOAWAY | 协议断路器和幂等 fallback |
| 切网 | Wi-Fi <-> 蜂窝、IP 变化、NAT rebinding | H3 迁移、旧连接淘汰、在途请求恢复 |
| 服务端 | 429/5xx、慢首字节、半开连接、大响应 | 优先级、熔断、取消和资源回收 |
| 稳定性 | 并发、长跑、反复建连/销毁 | ASan/TSan/LSan、崩溃率、句柄泄漏 |

### 11.2 发布指标与护栏

每次灰度至少按网络类型、运营商/地域、IPv4/IPv6、协议和请求优先级分层比较：

- 主指标：任务成功率、关键请求成功率、TTFB/Total P95/P99、切网恢复时长、白屏率。
- 护栏：请求量、重试放大、fallback 比率、服务端负载、耗电、流量、崩溃率、TLS/证书错误。
- 回滚：主指标无改善或任一护栏恶化超过预设阈值，自动关闭配置并保留请求证据供复盘。

## 12. 过时或高风险实践清单

| 实践 | 不应直接采用的原因 | 替代方案 |
| --- | --- | --- |
| 固定 MSS=1400、Socket 缓冲区、拥塞窗口 | 现代系统会根据 PMTU、BDP 和网络动态调优，应用硬编码可能降低兼容性 | 减少传输字节、连接复用、协议和服务端协同 |
| 固定初始 RTO=3 秒 | RFC 6298 使用动态 RTT/RTO 估计；固定值会损害快网或弱网 | 端到端 deadline + 分阶段超时 + 指数退避 |
| `tcp_tw_recycle`/`tcp_tw_reuse` | 前者已废弃，NAT 场景会拒绝合法连接；后者也不是移动客户端通用解 | 连接复用和服务端容量治理 |
| 关闭 Nagle 或强制 `TCP_NODELAY` | 小包延迟与网络开销存在权衡，不能作为 HTTP 通用开关 | 合并业务写入，基准测试后按协议/业务启用 |
| Hook DNS 或修改 Native ELF 接管 `getaddrinfo` | 系统升级、第三方 SDK、完整性和稳定性风险高 | 在统一网络库的 resolver 抽象层实现 |
| 关闭证书校验/HTTP 降级 | 会引入中间人攻击与数据泄露 | 正确保留 Host、SNI、证书主机名校验 |
| 0-RTT 发送写操作 | 存在重放风险 | 仅显式幂等请求使用，服务端校验重放 |
| 无预算的多 IP 竞速、预连接、探测与重试 | 放大流量、耗电、服务端压力并掩盖故障 | 限制次数/并发/时长，指标验证，远端回滚 |
